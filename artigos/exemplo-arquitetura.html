Cache em Duas Camadas para APIs de Leitura Intensa

Status · artigo de demonstração · não é conselho de produção

Resumo

Este artigo é um exemplo fictício usado para validar a formatação do site: numeração de seções, listas, tabelas comparativas e blocos de código. O "problema" descrito — cache em duas camadas para reduzir carga em um banco relacional — é ilustrativo e não corresponde a nenhum sistema real.

1. Contexto

Considere uma API que serve majoritariamente leituras, com um punhado de escritas por minuto e picos de tráfego previsíveis. O banco primário aguenta a carga normal, mas satura nos picos. Duas estratégias de cache concorrem: um cache local por processo (rápido, mas inconsistente entre réplicas) e um cache compartilhado (consistente, mas com um salto de rede a mais).

2. Decisões de arquitetura

  1. D1. Cache local (em memória) como primeira camada, com TTL curto — absorve picos de curtíssimo prazo sem round-trip de rede.
  2. D2. Cache compartilhado como segunda camada — mantém réplicas consistentes entre si e sobrevive a reinícios de processo.
  3. D3. Invalidação por evento, não por polling — uma escrita publica um evento que expira as duas camadas, em vez de esperar o TTL vencer.
