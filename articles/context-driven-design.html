Context-Driven Design: Self-Contained Vertical Modules for Go Services under Human and Machine Context Constraints

A pragmatic architecture for locality of behavior, dual-transport delivery (JSON API and server-rendered hypermedia), single-binary deployment, and testability

Igor Barbosa de Carvalho · linkedin.com/in/igor-carvalho-se

Revision 5 · July 2026 · Go ≥ 1.21 · Echo v4 · Status: working paper

Abstract

Purist layered architectures — Clean, Onion, Hexagonal — impose indirection costs that Go's design philosophy neither requires nor rewards. In parallel, a new consumer of source code has emerged: the large-language-model coding agent, whose finite context window converts architectural dispersion into a measurable, per-request cost. This paper formalizes Context-Driven Design (CDD), a vertical-slice architecture in which every feature is a self-contained module that owns its configuration, business rules, persistence, transport, and user interface, and attaches to a thin platform through an explicit dependency container. We present a reference implementation on the Echo framework covering module wiring; a machine-facing JSON API transport (§5); a human-facing hypermedia (HTMX) transport compiled into a single binary via go:embed (§6); lifecycle orchestration with graceful shutdown (§7); and a comparison of the static dependency container against a generics-based registry (§4.1). We then audit the original specification and identify nine gaps — including transport conflation, lifecycle defects, an error-handling fall-through, and undefined inter-module communication — and resolve all nine in this revision — the defects inline in the corrected listings, the design omissions as concrete specifications in §10. We argue that delete-ability and context-window footprint deserve treatment as first-class non-functional requirements, and give the latter a concrete, CI-enforceable measure: the Feature Context Footprint (§3.3).

Keywords — Go; software architecture; vertical slice; modular monolith; deployment topology; locality of behavior; Echo; bounded context; HTMX; hypermedia; JSON API; LLM-assisted development; testability.

1. Introduction

Go's founding premise — clarity over abstraction — sits uneasily with architectural doctrines imported from the Java and C# ecosystems. Clean Architecture [1] and Hexagonal Architecture [2] mandate indirection whose cost is fixed (ports, adapters, per-layer data models, mapping code) but whose benefit is contingent on a volatility that most CRUD-heavy services never exhibit. In Go the tax compounds: single-method interfaces declared "just in case," package sprawl that turns a one-line change into a four-directory expedition, and translation layers that outweigh the business rules they claim to protect.

A second, newer pressure has made the cost of dispersion explicit. LLM coding agents are now routine collaborators, and their working memory is a context window. An architecture that scatters a single feature across controllers/, usecases/, entities/, and gateways/ forces one of two failure modes on the agent: assemble a massive cross-cutting context (token cost, truncation, retrieval error) or operate on a partial view and produce architectural hallucinations — plausible code that references layers, interfaces, or conventions that do not exist in the repository. What was once an ergonomic complaint is now a metered expense, paid on every request.

Context-Driven Design answers both pressures with one move: each feature is a vertical slice, packaged as a self-contained module that plugs into a deliberately thin platform. The name is a double entendre by design — context as in the bounded context of domain-driven design [3], and context as in the context window of the machine reader.

This paper makes four contributions:

  1. C1. A formalization of CDD as six principles (§3.1), including two non-functional requirements rarely stated explicitly: delete-ability and context budget, the latter operationalized by the Feature Context Footprint metric (§3.3).
  2. C2. A reference implementation: an explicit dependency container (weighed against a generics-based registry in §4.1), plugin-style module wiring on the Echo framework, single-binary hypermedia delivery via go:embed, and a corrected process lifecycle (§4, §7).
  3. C3. A clean separation of the two transport surfaces that the original specification conflated — a machine-facing JSON API (§5) and a human-facing HTMX hypermedia layer (§6) — layered over one shared service core.
  4. C4. An audit of the original specification identifying nine gaps with severities — all nine resolved in this revision, the defects inline in §5–§8 and the design omissions as specifications in §10.1–§10.5.

A note on notation: the gap identifiers G1–G9 used throughout are cross-references into the consolidated audit of §10, where Table 2 defines each. The paper deliberately presents the corrected design first and the diagnosis afterward; a G-reference encountered before §10 simply marks the point where that gap's fix lives.

2. Background and Related Work

Layered doctrines. Clean [1] and Hexagonal [2] architectures optimize for substitutability of the outer rings — swap the database, swap the delivery mechanism — under the assumption that such substitutions are frequent enough to amortize permanent indirection. The Go community's counter-position is idiomatic rather than doctrinal: "a little copying is better than a little dependency" [8], interfaces belong to consumers rather than implementations, and style guidance such as Uber's [7] favors explicit construction and fail-fast validation over container magic.

Vertical slices and deployment topology. CDD is a Go-native instantiation of Vertical Slice Architecture [4], with one deliberate divergence: where .NET slices typically route requests through a mediator/dispatch layer, CDD wires everything at compile time with plain constructors, so the compiler — not a runtime dispatcher — is the integration test. On deployment, a word of caution is owed: the default shape is a modular monolith [9], but the architecture itself is deployment-agnostic. A module's only contract is Initialize(*server.Container) error, so it is the composition root — not the module — that fixes the topology. One binary attaching every module is a monolith; one binary per module is a microservice fleet; any grouping in between is a wiring decision in main() (§11, Listing 15). "Monolith" names a starting point, never a ceiling.

Relation to hub-and-spoke. Figure 1 invites the comparison: a Container at the center, modules radiating outward — a hub-and-spoke topology in the integration-architecture sense [11]. The analogy holds where it is useful. Like a hub, the platform is the single shared point through which capabilities are provisioned; like spokes, modules know the hub and never each other, so attaching the N+1th module costs one edge rather than N. But the analogy breaks exactly where it matters operationally: in messaging-era hub-and-spoke, the hub mediates every message at runtime, concentrating throughput and becoming a single point of failure. CDD's hub mediates only at boot — once Initialize returns, requests flow from router to handler to database with no central broker on the path. CDD is therefore hub-and-spoke in its dependency graph and point-to-point in its data plane, and the facade protocol (G4, §10.1) extends the same discipline to the few sanctioned spoke-to-spoke edges.

Locality of behavior. Gross states the principle for user interfaces: the behavior of a unit of code should be obvious by inspecting that unit alone [5], a stance elaborated into a full hypermedia-driven methodology in [6]. CDD generalizes the principle from the UI element to the entire slice — SQL, rules, routes, and markup live and die inside one folder — and adopts HTMX precisely because it keeps rendering on the server, collapsing the frontend/backend split that would otherwise reintroduce dispersion through a second repository and build pipeline.

3. The Context-Driven Design Method

3.1 Principles

  1. P1 — Locality of behavior. The unit of comprehension, code review, and prompt assembly is the module folder. Everything required to understand a feature — rules, queries, routes, templates, configuration — lives inside it [5].
  2. P2 — Modules are plugins. A module exposes exactly one entry point, Initialize(*server.Container) error. It is attached to the application at boot, never woven through it.
  3. P3 — The platform is boring. internal/platform provides infrastructure (router, connection pools, telemetry) and must contain zero business vocabulary. Dependencies point in one direction only: module → platform.
  4. P4 — Wiring is code. No DI container, no reflection, no code generation. The Go compiler is the dependency injector; a missing dependency is a compile error, not a runtime surprise.
  5. P5 — Delete-ability is the metric. Removing a feature must be rm -rf internal/<feature> plus one line in the composition root. If deletion requires surgery, locality was already violated. The guarantee covers code; data follows a protocol — the module's final migration is its teardown (§10.3) — because code deletes in O(1) and data never does.
  6. P6 — The context budget is a non-functional requirement. A slice should fit, whole, inside the working context of an agent — or a new hire. Token footprint per feature is tracked like binary size or p99 latency; §3.3 makes the budget measurable.

3.2 Canonical Topology

Listing 1 shows the directory layout. Three refinements over the original specification are visible immediately: the transport layer is split into api.go and web.go — one file per audience, anticipating §5–§6 and remediating gap G1; the module owns its own migrations/ directory, so the schema of a bounded context travels with the context (G7, §10.3); and facade.go marks the module's only sanctioned surface to siblings (G4, §10.1).

3.3 Quantifying the Context Budget: The Feature Context Footprint

P6 remains rhetoric until it is measurable, so this section gives it a number. Define MinSet(f) as the minimal set of files sufficient to modify feature f correctly — everything a competent agent (or developer) must hold in working context to change f without hallucinating structure. The Feature Context Footprint is the token mass of that set. In an arbitrary architecture, MinSet must be discovered, and the discovery itself consumes context; CDD's structural claim is that MinSet is statically enumerable — the module folder, the platform contract, and whichever facades the module imports:

FCF(f) = T(modulef) + T(container) + Σg ∈ facades(f) T(g)(1)

where T(·) is a token count, approximated for Go source by bytes ÷ 3.5 — tokenizer-dependent, but stable enough for comparison. From (1) follows the locality ratio, the fraction of a feature's required context that the feature itself owns:

L(f) = T(modulef) / FCF(f)(2)

CDD targets L ≥ 0.9, and the target is not arbitrary: the container is deliberately tiny (P3) and facades deliberately narrow (§10.1), so every point of L lost is either a fattening platform or a widening facade — precisely the two failure modes §4 and §10.1 exist to police. In a layered codebase L is both lower and, worse, undefined without dynamic discovery: the numerator has no folder.

The budget itself is an inequality, FCF(f) ≤ B. What sets B is no longer the raw window — modern windows exceed most codebases — but effective attention: retrieval quality degrades measurably as relevant material dilutes across long contexts [12]. As an engineering bound rather than a standard, this paper proposes

FCF(f) ≤ B,  B ≈ 30–50 k tokens (~120–200 KB of source)(3)

comfortably inside the regime where current models retrieve reliably; a slice approaching B is a candidate for splitting along an interior sub-boundary. Measurement is a shell one-liner — find internal/auth -type f | xargs wc -c, divided by 3.5, plus the container and imported facade files — cheap enough to run in CI on every commit.

Version history then validates the architecture retroactively. Define change cohesion as the median, over feature commits, of the number of distinct top-level directories touched:

C = mediancommits |{top-level dirs touched}|(4)

CDD predicts C = 1 (platform commits excepted); sustained drift above 1 is an early warning that the drawn boundaries no longer match how the system actually changes. Together (L, FCF, C) make P6 auditable: fail the build when L < 0.9 or FCF > B — the same fail-fast posture the architecture applies everywhere else.

4. The Platform Contract

To keep module signatures stable as the system grows, the platform's entire offering is encapsulated in a single struct (Listing 2). Growth is additive — a new field is invisible to modules that ignore it — and the container is passed by pointer so a future field never silently diverges between copies. The one governance rule is P3: the container carries infrastructure, never business services. The moment a domain type appears on it, it has become a god object and the boundary has failed.

The module's entry point (Listing 3) is where P2 and P4 meet: explicit constructors, fail-fast configuration, and error wrapping so that boot logs carry module-qualified causes. Note what the function does not know — how the database was opened, which port the server binds, or that any other module exists.

4.1 Design Alternative: A Generic Registry

A fair challenge to Listing 2: why a static struct, whose fields every module can nominally see, rather than a dynamic map from which each module resolves exactly the dependencies it needs? Generics make the alternative pleasant to express (Listing 4), and it deserves an honest comparison rather than a dismissal.

The struct buys three properties. Totality is compiler-checked: a module asking for a capability the platform lacks is a compile error today, not a boot error on deploy day (P4). Discovery is greppable: "who uses the database?" is one search over deps.DB, and the platform's entire offering reads as one type in godoc. And the visibility objection is weaker than it first appears: fields are offers, not obligations — a module that never touches deps.Tracer carries zero coupling to it, and the Go compiler will not even force the import. The registry buys the mirror image. Open extension: a third-party or generated module can contribute and consume capabilities without anyone editing a shared file. Minimal knowledge: a module names only the types it resolves. Its costs are the classic service-locator costs: errors move rightward from compile time to boot time, the dependency graph vanishes from static analysis, and the pattern is — structurally — the DI container that P4 exists to keep out.

The recommendation follows the trade-off rather than taste. Prefer the struct while the platform surface is small and first-party, which is the regime this paper targets; reach for the registry — or the hybrid of a struct carrying one Registry field for extensions — only when plugin-style third parties or unbounded capability growth turn editing container.go into a governance problem. The break-even is ownership, not field count.

5. Transport I — The JSON API

The original specification served both audiences from one handler, sniffing the HX-Request header to decide between JSON-era logic and HTML rendering. That conflation is gap G1: machine clients and browsers have incompatible contracts. Machines need versioned paths, strict content types, semantic status codes, and error bodies that are stable enough to program against; none of that should be entangled with template execution. CDD therefore gives each module two transport files over one service core (Figure 2), and this section specifies the machine-facing half in isolation.

Four rules govern the JSON surface. (i) Namespacing: every machine route lives under /api/v1/<module>/…, keeping versioning explicit and leaving root paths to hypermedia. (ii) Error envelope: failures return a stable {code, message} object; clients branch on code, never on prose. (iii) Defense at the edge: request bodies are bounded by the platform's BodyLimit middleware (§10.2) before any handler runs. (iv) Translation, not logic: the handler maps domain sentinel errors to HTTP status codes and does nothing else — no SQL, no templates, no business branching. Listing 5 registers both surfaces on the Echo router [10]; Listing 6 implements the API handler.

Route governance across modules (G9) survives the framework change through one explicit assertion: after the last Initialize, the composition root calls server.MustAssertUniqueRoutes (Listing 13, §10.5), so a cross-module route collision is a boot failure rather than a silently shadowed handler in production.

6. Transport II — Serving Hypermedia (HTMX)

The human-facing surface returns hypermedia, not data. Templates are embedded with go:embed and parsed once at package initialization (Listing 7): the back end and the front end compile into a single binary, and a malformed template kills the process at start-up — or a trivial CI test — rather than mid-request. This corrects the original design, which parsed inside the constructor and thereby deferred discovery of template defects.

The fragment protocol is the heart of the layer. HTMX marks its requests with HX-Request: true; on validation failure the handler responds with 422 Unprocessable Entity and re-renders only the _form.html fragment (Listing 8), which HTMX swaps in place. A non-HTMX browser hitting the very same route receives the full page with the error inlined — progressive enhancement with zero JavaScript build step. Success diverges symmetrically: HTMX clients get an HX-Redirect header with 204 No Content; classic browsers get 303 See Other. Listing 7 makes every branch explicit — the original listing's error path fell through to the success redirect for non-HTMX clients (G3), a defect invisible in a demo and severe in production.

7. Composition Root and Lifecycle

The entrypoint owns exactly three jobs: build the platform, attach the modules, and manage the process lifecycle. The original listing carried three defects worth naming (G2). First, log.Fatalf inside the serving goroutine calls os.Exit, which skips every defer — including db.Close() — precisely in the crash scenarios where orderly release matters most. Second, the shutdown check compared errors with !=, which breaks silently the day an error is wrapped; errors.Is is the durable form. Third, the server carried no timeouts, leaving it exposed to slow-client exhaustion, and its five-second drain window is aggressive for anything long-lived.

Listing 9 applies the canonical fix: main delegates to a run() error function that holds every resource and every defer, giving the process a single exit point through which clean-up always flows. signal.NotifyContext replaces the hand-rolled channel, and explicit timeouts bound both request handling and drain.

8. Testability

The vertical slice makes each testing tier structurally cheap — but only once one inconsistency in the original specification is resolved. The prose promised unit tests that mock "the repository interface," while the code constructed a concrete *Repository: a claim the type system could not cash (G6). The Go idiom resolves it — accept interfaces, return structs — with the interface declared by its consumer and kept minimal (Listing 10). A three-line stub then replaces the database, and service tests run in microseconds with zero infrastructure. The rule generalizes, and deserves stating as sharply as the principles of §3.1: a feature-oriented architecture does not abolish interfaces, it abolishes speculative ones. A seam exists wherever a consumer must substitute a collaborator under test; it is declared in the consumer's file, sized to exactly the consumer's use, and satisfied implicitly by the concrete type. Mockability is thereby a property each slice grants itself, never a ceremony imposed architecture-wide.

For integration, the module's own Initialize doubles as the test harness: inject a throwaway Postgres from Testcontainers and a fresh platform router, and the test exercises real SQL, real wiring, and real routes exactly as deployed (Listing 11). Because the parsed-at-init templates of §6 live in package state, a one-line test — importing the package and asserting nothing — already proves every template parses.

End-to-end, the hypermedia choice pays again. The module serves its own HTML, so Playwright drives the genuine routes with no SPA build, no API-mocking layer, and no hydration races; an HTMX swap is an ordinary HTTP round-trip whose result is directly assertable in the DOM. The three tiers compose into a clean pyramid whose every level lives inside — or points directly at — the module folder.

9. Trade-off Analysis

Table 1 compares CDD against a purist layered baseline along the dimensions this paper treats as decision-relevant. The honest reading is not one-sided. Layered designs retain a genuine advantage wherever cross-cutting invariants dominate — heavily regulated domains with many shared policies have a natural home for them in a layer, whereas CDD must build that seam deliberately (G5). Duplication of near-identical data structures across modules is real; CDD accepts it as the standard price of bounded contexts [3] and of the copying-over-coupling proverb [8]. And module count itself can sprawl: past roughly twenty slices, grouping folders by subdomain restores navigability without breaking any principle. The framework choice deserves the same candor: Echo trades a measure of P4's stdlib purism for binding, route groups, and native middleware — a trade this design contains by keeping the framework a guest rather than a landlord, mounted behind http.Handler (Listing 9) and visible to modules only through RegisterRoutes, so it stays reversible.

10. Gap Analysis and Resolutions

Auditing the original specification against the principles of §3.1 yielded nine gaps. This revision closes all nine. Four are resolved where the corrected listings live — the transport conflation in §5–§6 (G1), the lifecycle defects in §7 (G2), the error fall-through in §6 (G3), and the untestable concrete coupling in §8 (G6). The remaining five are specified in the subsections below: inter-module communication (§10.1), the cross-cutting seam (§10.2), schema ownership (§10.3), observability (§10.4), and route governance (§10.5). 10.1 G4 — The Facade Protocol

Sibling isolation is CDD's structural guarantee, but real systems eventually need billing to verify a token that auth issued. The remediation is a deliberately narrow, exported facade: one small file whose interface is the only symbol siblings may touch (Listing 12). The fence is then made mechanical rather than cultural with an import linter (depguard or gomodguard): internal/<m>/** may import internal/platform/** and sibling facades, nothing deeper. Where even a facade couples too tightly — notification-style, fire-and-forget integration — a small in-process event bus carried on the Container removes the temporal coupling as well.

10.2 G5 — The Cross-Cutting Seam

Echo dissolves what the stdlib design had to hand-build: middleware is native, and the seam lives exactly where P3 demands — in the platform, installed once, invisible to modules (Listing 13). The chain is ordered deliberately. Recovery sits outermost, so a panicking handler becomes a logged 500 instead of a dead process; the request ID precedes logging, so every line is correlated; the 1 MB body limit runs ahead of any decoder, generalizing §5's edge guard from one handler to the entire surface; and OpenTelemetry wraps innermost, so spans measure real work. Modules stay policy-free, with one carve-out unchanged from the earlier design: authorization on a module's own routes stays inside the module, because the module owns that vocabulary — and Echo's group-level middleware makes that local attachment a one-liner in routes.go.

10.3 G7 — Schema Ownership and Migrations

Locality that covers queries but not DDL is locality half-kept — but the naive fix, a migrations folder per module wired together by hand, has three failure modes of its own. A hand-maintained aggregation map is a second registry that can silently omit a module, deferring the failure from boot to the first query. "Disjoint schemas, so order is immaterial" holds only until someone declares a cross-module foreign key. And a ledger fragmented per module leaves operations without a single answer to the only question that matters at 3 a.m.: what version is production on? The resolution splits authorship from operation: folders stay per module, because ownership is a code-locality concern; the ledger is global and singular, because schema state is an operational one.

Four rules make the split safe. Pure SQL. The migration artifact is a .sql file a DBA can read in a pull request; an established engine — goose, golang-migrate, or Atlas in versioned mode — owns history, checksums, and dirty-state detection; Go's role is embed-and-invoke, nothing more. Go-code migrations and ORM auto-migration are banned: an unversioned, reflection-driven schema sync is not a migration, it is a hope. One registry. The module registers its embedded SQL inside Initialize (Listing 3), so forgetting a schema would require forgetting the module — which fails loudly anyway. One ledger. Filenames are timestamped and module-prefixed (20260714120000_auth_create_users.sql); the platform migrator merges every registered filesystem, sorts the stream chronologically, and applies it under a Postgres advisory lock, so N replicas booting together cannot race the DDL, and history lives in exactly one table. No cross-module constraints. Modules share identifiers, never foreign keys — the same doctrine as the facade (§10.1), and forced regardless by the extraction path of §11: a module promoted to its own database could not have kept the constraint. A genuine need for a cross-context FK is evidence that one context has been drawn as two.

When to apply is a separate decision from how, and the answer is: at deploy, not at boot. Applying DDL from the serving process requires the runtime credentials to hold DDL rights forever — so any injection or RCE in the request path inherits DROP TABLE — and couples rollout to schema work, so a slow CREATE INDEX stalls the fleet's readiness probes. The embedded SQL makes the production shape nearly free (Listing 14): the same binary grows a migrate verb, run once per deploy as a pipeline job under a privileged role, while the serve verb boots under DML-only credentials and merely verifies, refusing to start behind the binary's newest known version (Listing 9). Auto-apply survives as a development-mode platform flag, where its convenience is real and its risks are not. For the single-pane view, CI dumps pg_dump --schema-only from a freshly migrated scratch database as a build artifact: the complete schema becomes one reviewable file, and drift is visible in pull requests.

One honest amendment to P5 follows. rm -rf deletes code in O(1); data never deletes in O(1). A module's final migration is therefore its teardown, shipped and applied before the folder is removed — otherwise strict engines error on history entries whose files have vanished, and orphaned tables outlive their owner. Delete-ability holds fully for code and by protocol for data, and §3.1 now says so.

10.4 G8 — Observability as a Platform Capability

Telemetry follows the same one-directional flow as every other capability. The container carries a trace.Tracer (Listing 2); the platform's middleware opens a span per request (Listing 13); and a module wanting finer grain wraps its service or repository calls in child spans via deps.Tracer — three lines, no global state, no sibling imports. Metrics are symmetric: a Meter field joins the container the day the first module needs one, and P3's additive-growth property guarantees no existing module notices.

10.5 G9 — Route Governance

Two mechanisms compose. The convention — /<module>/… for hypermedia, /api/v1/<module>/… for machines — makes collisions unlikely by construction. The assertion makes them unshippable: server.MustAssertUniqueRoutes (Listing 13) walks e.Routes() after the last Initialize and panics on any duplicate method–path pair, restoring the boot-time fail-fast that the stdlib mux provided through its registration panic and that Echo's more permissive router does not guarantee. A collision between modules is therefore a deploy that never starts, not a handler silently shadowed in production.

11. Conclusion and Future Work

Context-Driven Design reframes an old ergonomic argument — vertical slices over horizontal layers — around a constraint that is newly measurable: the finite context of the reader, whether human or machine. Its six principles cost little to state and much to violate, and the reference implementation shows the whole method fitting comfortably inside idiomatic Go: an explicit container, plugin modules, two cleanly separated transports over one service core, and a lifecycle that survives its own crashes. The audit is part of the argument rather than an appendix — a design that advertises legibility should welcome having its own listings read closely, and three of the nine findings were bugs that close reading caught. In this revision the ledger closes at nine for nine.

A terminological caution belongs in the conclusion, because it changes how the whole method should be read: this paper has used "modular monolith" for the default deployment shape, and the word monolith deserves its qualifier. Nothing in CDD binds a module to a single process. Because the platform contract is the module's only coupling, the same slice compiles unchanged into whichever binary attaches it (Listing 15): every module in one cmd/api (a monolith), one module per binary (a microservice fleet), or domain-grouped clusters in between. Topology is configuration held in the composition root; when modules split across binaries, cross-module calls simply flow through an RPC implementation of the G4 facade instead of the in-process one. The monolith is merely the cheapest place to start — the architecture is deployment-agnostic.

Two lines of future work follow directly. Empirically, §3.3 turns the context-budget claim into an experiment: hold tasks constant, vary architecture, and regress agent task-success against FCF and L on matched CDD and layered codebases — the metric supplies the independent variable that was previously missing. Operationally, the extraction protocol deserves specification: a checklist by which a module that outgrows the monolith — facade to RPC, migrations to its own database, events to a broker — leaves through the seams this architecture already drew.
