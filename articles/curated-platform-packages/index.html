Curated Platform Packages: A Small, Composable Standard Library for Context-Driven Systems

Specifying the boring half of P3 — reusable, agent-legible infrastructure primitives shared across vertical modules, and the amortized economics that justify curating them

Igor Barbosa de Carvalho · linkedin.com/in/igor-carvalho-se

July 2026 · Go ≥ 1.21 · Companion to Context-Driven Design

Abstract

Context-Driven Design (CDD) [1] resolves where code lives: a feature is a vertical module, the platform beneath it is deliberately thin, and P3 requires that thin layer to carry "zero business vocabulary." What CDD leaves unresolved is what already exists — nothing in its six principles stops two modules, or two agent sessions authoring those modules months apart, from independently hand-rolling their own error type, their own config loader, their own graceful-shutdown routine. This is not hypothetical: three of the nine gaps CDD's own reference implementation audited against itself — the lifecycle defects (G2), the error fall-through (G3), and the untestable concrete coupling (G6) — are instances of exactly this failure mode, discovered inside a paper explicitly designed to avoid it. This paper proposes Curated Platform Packages (CPP): a small number of hand-reviewed, generic, single-purpose Go packages held at pkg/, admitted by a four-part test (§3) that extends P3's "zero business vocabulary" rule to infrastructure code generally, and made discoverable to coding agents through machine-legible package headers and an explicit reuse-before-writing clause (§5). We give a worked catalogue of eight reference packages (§9) covering error handling, structured logging, configuration, lifecycle, database access, and migrations; a governance protocol for admitting and deprecating packages without the library becoming a second god-object (§7); and an economic argument — the Library Break-Even (§6) — for when curation stops being premature abstraction and starts paying for itself, extending CDD's own Feature Context Footprint metric to the case of shared, cached, repeatedly-read dependencies rather than freshly generated code. We close by proposing pkg/ as a deliberate, narrow instance of Evans's Shared Kernel [2] — dangerous when applied to domain models, safe here precisely because P3 already forbids the domain vocabulary that makes sharing dangerous.

Keywords — Go; internal standard library; shared kernel; vertical slice architecture; LLM coding agents; software reuse economics; developer experience; prompt caching; context-driven design.

1. Introduction

Context-Driven Design [1] makes a sharp argument: an architecture optimized for a finite-context reader — human or machine — should minimize how many places a change touches. Its answer is the vertical module: one folder per feature, owning its rules, its queries, its transport, its templates. The platform beneath it is kept deliberately boring (P3), and wiring is compile-time and explicit (P4) precisely so that nothing magic stands between a module and the infrastructure it depends on.

That design closes the question of placement and opens a different one: provenance. When a new module needs to load configuration from the environment, wrap a database error with an operation trace, or shut down cleanly on SIGTERM, where does that code come from? CDD's platform contract (its Listing 2, the Container struct) supplies live infrastructure — a router, a connection pool, a logger instance — but it says nothing about the code that knows how to use them correctly. In a codebase written module-by-module by a coding agent operating under P4's "the compiler is the dependency injector," the default answer is: that code gets written again, inside the module, every time it is needed. Locality of behavior is preserved — the code is right there, in the one folder P1 asks it to be in — but at the cost of an invisible tax: the same twenty lines of graceful-shutdown boilerplate, or the same domain-error type with a slightly different field name, re-derived per feature, per session, occasionally per agent, with no guarantee any two derivations agree.

The evidence that this tax is real is not conjectural — it sits inside CDD's own worked example. §10 of that paper audits its reference implementation against its own six principles and finds nine gaps. Read the ledger with an eye for provenance rather than symptom, and a pattern appears: G2 (a Fatalf inside a goroutine that skips every deferred cleanup, a fragile != error comparison, no server timeouts) is not an auth-module bug — it is generic process-lifecycle code, hand-written once, inside a main.go that had no library to call instead. G3 (a failed login falling through into the success redirect) is exhaustive-branching discipline that a shared response-writing helper would have made structurally impossible to skip. G6 (a service bound to a concrete repository, unable to honor the testing story the prose promised) is a consumer-side-interface convention that a template or a linter, not tribal memory, should enforce. None of these three gaps is a business-logic defect. All three are boring, generic, and — this paper's central claim — exactly the class of code that should never be written twice.

This paper specifies that missing layer. Curated Platform Packages (CPP) are a small set of hand-reviewed Go packages held at pkg/, sitting beside internal/platform but distinct from it: platform is live infrastructure a module borrows through the Container; pkg/ is compiled-in behavior a module imports directly, the same way it imports the standard library. The contribution is not "write a utils folder" — every codebase already has one, and most decay into exactly the dumping ground CDD's P3 was written to prevent platform from becoming. The contribution is an admission test that keeps the library small on purpose (§3), a set of idioms that make each package trivially auditable in isolation (§4), a discoverability protocol that lets an agent find a package before reinventing it rather than after (§5), and an economic argument for why the curation effort is worth it once a package crosses a small, computable usage threshold (§6).

2. Background and Positioning

The Go pkg/ convention, and its failure mode. A top-level pkg/ for code "safe for external use" is old Go folklore, popularized by Bourgon's widely cited note on repository structure [5] and canonized informally by the community project-layout repository [6] — itself contested precisely because it prescribes a folder without prescribing an admission rule. In practice, an undisciplined pkg/ becomes the same god-object CDD's P3 warns against for internal/platform: a junk drawer that accretes one export per contributor's convenience, coupling every module to it by habit rather than by need. This paper's position is that the folder was never the problem — the missing admission test was. §3 supplies one.

Shared Kernel. Evans names the pattern of two bounded contexts explicitly agreeing to share a small subset of code, with the caveat that the shared subset must stay small, changes must be negotiated, and — critically — it must not carry the domain model of either context, on pain of recoupling what bounded contexts exist to decouple [2]. CDD already prohibits exactly that vocabulary from crossing into its platform layer (P3); this paper's claim is that the same prohibition, applied to a library modules pull from rather than a container modules are handed, is what makes a Shared Kernel safe to use as pervasively as an internal standard library rather than sparingly as Evans' original warning implies. §8 makes the mapping precise.

LLM coding agents change the calculus, not the principle. "Don't repeat yourself below a threshold" is old advice — Go's own proverb, "a little copying is better than a little dependency" [3], counsels the opposite bias for a reason: premature abstraction is a real cost, and CDD itself invokes the proverb to justify accepting duplication of near-identical data structures across bounded modules. Nothing here overturns that. What changes is the threshold's shape. A human engineer writing the same lifecycle boilerplate for the third time notices the repetition and feels the itch to extract it. An agent operating one module at a time, each session bounded by CDD's own context budget (P6), has no memory of the first two derivations unless something in the repository tells it they exist. Left alone, the proverb's "little copying" silently compounds past "little" — not from bad judgment, but from the absence of the very continuity a human maintainer supplies for free. §5 and §6 give that continuity back.

3. The Three-Way Partition

CDD draws one boundary: module versus platform, with dependencies flowing one way (P3). This paper draws a second boundary inside "platform," splitting it into live infrastructure a module receives (the Container) and compiled-in behavior a module imports (pkg/). Figure 1 gives the resulting topology and its one new rule: pkg/ is a leaf. It may import the standard library and a short, explicitly allow-listed set of external dependencies; it may never import anything under internal/. Enforcement is the same mechanism CDD already prescribes for its facade fence (G4, §10.1) — a single depguard/gomodguard rule, extended by one line: pkg/** may not import internal/**, full stop. A package that needs something module-specific to compile has failed the test in the first place (A1, below) and belongs inside the module, not in the library.

Admission to pkg/ is a conjunction of four tests, deliberately conservative because the failure mode of a shared library is asymmetric: an unwarranted rejection costs one duplicated file; an unwarranted admission costs a coupling point every module downstream must now carry forever.

  1. A1 — Zero business vocabulary. The same test P3 already applies to internal/platform, applied here to code modules import rather than infrastructure they are handed. A type named Invoice or Session disqualifies a package on sight; a type named Error or Manager does not.
  2. A2 — Parametric, not particular. The package must work for any caller without editing the package — via generics (must.Get[T]), a consumer-declared interface, or functional options — never via a switch statement keyed on which module is calling.
  3. A3 — Leaf-only imports. Standard library and a short allow-list of externals; never internal/**. Mechanically enforced (§3, above), not culturally hoped for.
  4. A4 — Two call sites, not one. A package earns admission on its second occurrence, not its first. The Go proverb [3] governs below the threshold — a single module's need for a helper stays inside that module, plainly duplicable, no library required. Extraction on the second sighting, rather than the classic "rule of three," is deliberate: agent-authored duplication is cheaper to introduce and easier to miss in review than human-authored duplication (§2), so the threshold that keeps copying "little" is lower here than folklore usually sets it.

4. Package Design Idioms

A2's "parametric, not particular" test has teeth only if the packages actually practice it. Four idioms recur across a working catalogue built on this pattern, each chosen for the same reason: keep the package's exported surface small enough that using it costs less context than writing the equivalent inline ever would (the exact comparison §6 formalizes).

Generics over reflection for the "fail fast or continue" shape. Bootstrap code is full of the pattern "run this, and if it errors, the process should not start." A generic helper collapses the pattern to a call rather than an if err != nil { log.Fatalf(...) } block repeated at every call site — precisely the class of code whose omission or misuse produced CDD's G2.

Structured errors that satisfy errors.Is/errors.As by construction. A domain error type carrying a machine code, a human message, an operation trace, and an Unwrap method gives every module the same error ergonomics without every module writing its own — and, because the type implements Is by comparing codes rather than pointer identity, a handler can branch on kind of failure without needing the exact sentinel value that produced it.

Context-aware logging that extracts correlation fields once. A thin wrapper over log/slog that pulls a fixed set of context keys (trace id, tenant id, correlation id) into every log line removes a second copy-pasted concern: the alternative is each module remembering, or forgetting, to attach the same three fields by hand.

Functional options for anything with more than one legitimate configuration. A database client that may or may not have a read replica is exactly the shape functional options exist for — WithWriter, WithReader — keeping the zero-argument case trivial while making the two-argument case explicit and self-documenting at the call site, without a constructor that grows a new positional parameter every time a new concern appears.

None of these four idioms is novel Go; the contribution is treating them as a closed, curated set rather than a grab-bag each contributor reinvents its own version of — which is exactly the discipline that keeps pkg/ from decaying into the junk drawer §2 warned against.

5. Discoverability for Agents

A library nobody can find is not reused, it is duplicated with extra steps. CDD's Feature Context Footprint (§3.3 of [1]) already argues that a slice's context should be statically enumerable rather than dynamically discovered; the same argument applies one level up, to the library itself. Two mechanisms make pkg/ statically enumerable to an agent without requiring it to read every implementation file.

Machine-legible package headers. Every package file opens with a short, structured comment — title, one-line description, package kind (Utility, Implementation, Package), last-reviewed date — ahead of the ordinary Go doc comment. The header is redundant with well-written prose documentation for a human reader, and that is exactly the point: it is also a fixed-shape record an agent (or a lightweight script) can grep across the whole library in one pass, without parsing Go, to answer "does something already do this?" before writing new code. The same header doubles as the admission record §7's governance process requires — one artifact, two audiences. The mechanism only holds if the header stays honest, though, and staleness fails in either direction: an agent that trusts a lagging header acts on false confidence, and one that has learned not to trust it falls back to reading the implementation anyway — which is precisely the context-window, rate-limit, and context-poisoning cost Listing 2 exists to avoid, paid in full on every package the header was supposed to make cheap. Keeping it honest cannot be left to author memory — it needs a pre-commit or CI hook that fails whenever a package's exported surface changes without a matching header edit, the same enforcement discipline any other statically-checked contract already gets in a CDD codebase.

The reuse-before-writing clause. The agent contract that already governs a CDD codebase (its own equivalent of an AGENTS.md) gains one addition: before authoring any function under a fixed list of headings — error handling, configuration loading, structured logging, graceful shutdown, database access, JSON (de)serialization — the agent greps pkg/ for a header whose description matches. It may write a bespoke inline version only if no package exists and the need fails A1 (it is genuinely module-specific); if a package exists but is insufficient, the contract requires extending it in place rather than shadowing it with a parallel inline implementation. This is the missing half of P4: the compiler already guarantees a module cannot wire a dependency that does not exist; this clause guarantees an agent does not silently manufacture one that already does.

6. Economics: The Library Break-Even

Curation has a cost — someone reviews, tests, and maintains each package — so the decision to extract one should be an economic one, not a taste one. Let w be the expected token cost of an agent authoring a bespoke equivalent inline: not merely the final lines of code, but the realistic cost of drafting, running, and fixing them, which CDD's own gap ledger suggests routinely exceeds the artifact's raw size. Let T(p) be the one-time cost of writing and reviewing package p, and r the marginal cost of a call site referencing it — dominated by Tpub(p), the package's exported surface (signature plus doc comment), since a competent caller reads what a function promises, not how it keeps that promise. For N modules that would otherwise each pay w:

Savings(p, N) = N·w − (T(p) + N·r)(1)

which is positive once N passes the break-even point

N* = T(p) / (w − r)(2)

Two properties of (2) matter more than its precision. First, because r ≈ Tpub(p) is small by design (A2's parametricity keeps exported surfaces narrow) while w includes the iteration cost of getting boilerplate right, the denominator is usually close to w itself — N* tends to be small, on the order of two or three uses, which is precisely A4's admission threshold rather than a coincidence: the admission rule and the economic break-even are the same inequality viewed from two directions. Second, r is paid on every read of the package regardless of N, but production LLM APIs discount repeated, unmodified context through prompt caching — a file that has not changed since the last request is markedly cheaper to include again than one generated fresh in the same turn. A hand-rolled inline block, invented anew in each session, can never benefit from that discount; a stable file at pkg/errors/errors.go structurally can. The Library Break-Even is therefore a lower bound on the case for curation, not the whole of it.

This also resolves an apparent tension with CDD's own P6. The Feature Context Footprint (its equation 1) treats every byte a module pulls in — including facades — as pure cost, and a naive reading might charge pkg/ imports the same way, penalizing reuse. The resolution is that FCF measures a single feature's read cost, while (1) measures the library's amortized write cost across the codebase's history. A shared package does add a fixed, small term to every importing module's FCF (§8 makes the term explicit) — but it removes a much larger, module-sized term that hand-rolled equivalent code would otherwise have contributed to T(modulef) itself. pkg/ is not exempt from the context budget; it is how a codebase pays that budget in bulk rather than piecemeal.

Translated out of notation, the saving is concrete rather than abstract. Every token an agent does not spend re-deriving apperr's Unwrap method for the fifth module in a row is a token it spends on that module's actual logic instead — and because production APIs bill per token and throttle per token-per-time-window, the saving is not merely faster, it is cheaper in dollars and it stretches a session further before running into the rate-limit wall §5 already warned about. The header in Listing 2 is what keeps r close to its theoretical floor: an agent that answers "does this exist?" from a nine-line frontmatter block never pays the far larger cost of reading, or worse re-writing, the file behind it, which is exactly the difference between r ≈ Tpub(p) and r ≈ w that (2) depends on holding. Multiply that gap by every call site a package like apperr or lifecycle accumulates, and the sums in (1) stop being a proof about counting and start being a line item on an API bill: fewer tokens drafted, fewer tokens re-read on every subsequent session, and fewer features that stall mid-implementation because an agent spent its budget re-inventing boilerplate pkg/ already solved.

7. Governance: Admission and Deprecation

A library with no gate decays into the dumping ground §2 described; a library with too heavy a gate never gets used. The process kept here is deliberately lightweight, sized for a small team or a solo maintainer working alongside agents rather than a platform organization with a review board.

  1. Admission. A package proposal is the header of Listing 2 plus a one-paragraph note citing the two call sites that satisfy A4. No separate design-doc process — the header is the record, kept in the file it documents rather than a wiki that drifts out of sync with it.
  2. Review. One human maintainer approves. This is the one place this paper insists on a human in the loop unconditionally: §4's idioms are simple, but a package's exported surface is a promise every future module inherits, and a promise is exactly the kind of decision CDD's P4 reserves for something more durable than a single agent's judgment in a single session.
  3. Deprecation. The header's kind field gains a Deprecated value and a superseded_by pointer; the reuse-before-writing clause (§5) treats a deprecated match as a warning to migrate rather than a green light to import. The package is deleted once its last caller is gone — the same delete-ability discipline P5 already applies to modules, applied here to the library that serves them.
  4. A living ledger. Known rough edges — "this package's transaction helper hasn't been stress-tested under concurrent panics," say — are tracked as short, file-and-line-anchored notes rather than left as inline TODO comments that rot silently. The ledger is as agent-legible as the headers it sits beside: a fixed structure an automated pass can sweep into tracked issues on a cadence, rather than a comment an agent might overwrite without ever surfacing it for human review.

8. Relation to Context-Driven Design

Three of CDD's own mechanisms extend cleanly to accommodate pkg/, and it is worth being precise about each, because the temptation to conflate "shared" with "central" is exactly what CDD's hub-and-spoke discussion (§2 of [1]) already warned against for the Container.

The Container is unaffected. Nothing here proposes adding fields to server.Container for library packages — pkg/ is imported directly by both modules and the platform, never injected, because injection implies a lifecycle and a substitution point that a stateless helper library does not need. The Container stays exactly what CDD's Listing 2 says it is: live infrastructure, nothing else.

The facade fence gains one clause. G4's import-fence linter, which already keeps sibling modules from importing each other directly, is the same mechanism §3 uses to keep pkg/ a leaf. One linter configuration now enforces two rules that were previously two separate concerns: modules talk to modules only through facades, and nothing talks up into internal/ from below.

The Feature Context Footprint gains one term. Equation 1 of [1] is

FCF(f) = T(modulef) + T(container) + Σg∈facades(f) T(g)

and extends, under this proposal, to

FCF′(f) = T(modulef) + T(container) + Σg∈facades(f) T(g) + Σp∈pkg(f) Tpub(p)(3)

using each package's exported surface rather than its full implementation, on the same reasoning as §6's r. Because Tpub is small and bounded independent of module count — the same eight-package catalogue serves every module in the system without growing — the new term is a near-constant addition to every feature's footprint, not a source of the drift P6 exists to catch. A codebase where FCF′ grows unbounded with each new module is telling a different, worse story: that pkg/ has stopped being a small shared kernel and started accreting module-specific special cases, which is precisely what A1 exists to forbid before it happens.

Shared Kernel, made safe by subtraction. Evans's original warning about Shared Kernel is that shared domain code recouples the bounded contexts it crosses, since a change on one side of the boundary now demands negotiation with the other [2]. CDD's P3 already forbids the vocabulary that makes that recoupling possible from ever entering the platform layer; A1 applies the identical prohibition to pkg/. What is shared here is never what the business means — only how to fail fast, log a line, or wrap a transaction — so a change to pkg/errors cannot leak a change in what "billing" or "auth" mean to each other. That is the condition under which a Shared Kernel stops being a hazard to negotiate carefully and becomes an internal standard library, usable as pervasively as the one the Go runtime itself ships.

9. Worked Catalogue

Table 1 gives a reference set of eight packages, drawn from a working implementation built under exactly this discipline, satisfying all four admission tests of §3. Its size is itself a claim: eight packages is not a framework, and staying near that order of magnitude — resisting the pull toward a ninth, tenth, twentieth package for every convenience a contributor can imagine — is A4's threshold doing its job.

Table 1 is not closed. These eight are the ones the working implementation this paper draws on happened to accumulate, and the ones worth walking through in print — not a ceiling on what pkg/ may ever contain. A concern that clears A1–A4 (§3) belongs in the catalogue regardless of whether it appears above, and a real codebase should expect the list to grow: retry-with-backoff, rate limiting, a cache abstraction, a pub/sub client wrapper are all plausible candidates that simply were not part of this particular system. The caution is not against growth but against the manner of it — §6's break-even and §7's admission gate exist precisely because each new candidate carries the same risk this paper has warned about since §2: a package admitted on convenience rather than accumulated call sites, or one that lets a scrap of domain vocabulary slip into its exported surface, re-couples the modules it touches and turns the Shared Kernel §8 declares safe back into the hazard Evans originally warned against. Every addition to this table earns its place the same way the first eight did — A4's call-site threshold first, a human reviewer second — or it does not belong in pkg/ at all.

Table 2 sets Curated Platform Packages against the two alternatives a codebase actually faces: reinventing infrastructure per module (the status quo an undisciplined CDD codebase drifts toward), and adopting a general-purpose framework that supplies the same concerns but at the price P4 already rejected — reflection, code generation, or a DI container standing between the compiler and the wiring.

11. Conclusion and Future Work

Context-Driven Design answered "where does this code live" with a principle sharp enough to enforce mechanically. This paper answers the question CDD leaves open — "has this code already been written" — with the same posture: a small admission test (§3), idioms that keep each admitted package legible on its own (§4), a discoverability protocol built for an agent's working memory rather than a human's tribal knowledge (§5), and an economic argument for when curation is premature and when it is overdue (§6). The two papers compose rather than compete: CDD keeps a feature's business code contained to one folder; this paper keeps a codebase's boring code from being re-derived, inconsistently, inside every one of those folders. Read together, they cover both halves of P6's context budget — what a module must contain, and what it should never have had to write in the first place.

Two lines of future work, chosen to reuse rather than duplicate the empirical program CDD's own conclusion already proposes. First, the FCF regression CDD calls for — agent task-success against FCF and L on matched codebases — extends directly to a within-subjects arm: the same task, the same architecture, with and without a curated pkg/, scoring defect rate against the specific class CDD's own audit surfaced (G2/G3/G6-shaped bugs) rather than defects generally. Second, the Library Break-Even (§6) is currently an estimate; instrumenting real agent sessions for w and r directly — token cost actually spent per boilerplate pattern, with and without a matching package available to find — would turn Equation 2 from a plausible model into a measured one, and would let A4's two-call-site threshold be checked against data rather than argued from first principles alone.
